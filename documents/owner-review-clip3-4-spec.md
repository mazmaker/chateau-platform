## 0. หลักการกลางที่เฮียย้ำ (ใช้ตัดสินทุกข้อ)

1. **โครงสร้างข้อมูล ใหญ่→เล็กเสมอ** = แพลตฟอร์ม → บริษัท → โครงการ → ยูนิต/ลูกค้า (คลิป3 บรรทัด 119-121, คลิป4 บรรทัด 107). ทุกหน้าต้องเริ่มจาก "ภาพรวม" (กราฟ) ก่อน แล้วค่อย drill ลง
2. **ภาพรวม = ดูกราฟก่อน ไม่ใช่ตาราง/ดรอปดาว** — กราฟมี 3 แบบ: เส้น / แท่ง / **วงกลม(โดนัท)**. เห็นกราฟปุ๊บต้องรู้ทันทีว่า "หัวขึ้นหรือหัวทิ่ม" / ก้อนไหนใหญ่สุด (คลิป3 บรรทัด 27-36)
3. **เสนอ Solution มา ไม่ใช่มาถาม "เฮียจะเอาอะไร"** — break down data เองได้ (ถาม AI ก็ได้) แล้วมาเสนอว่าทำไมถึงเลือกแบบนี้ (คลิป4 บรรทัด 176, 184). นี่คือสิ่งที่ทำให้ CHATEAU ต่างจาก "ซอฟต์แวร์เฮาส์"
4. **Owner ต้องรู้ทุกมิติของ data ข้ามบริษัท** แต่ไม่ใช่ไป "แก้ไข/manage" ของบริษัทอื่น — แค่ "เรียกข้อมูลขึ้นมาดู" ได้ (คลิป2 บรรทัด 183-186; Facebook analogy คลิป2 บรรทัด 187)
5. **PDPA / Consent คือเส้นตาย** — ทุกจุดที่เซลล์เก็บข้อมูลลูกค้าผ่าน device ของแพลตฟอร์ม ต้องมี consent (คลิป3 บรรทัด 92-108)

## 1. P0 — ต้องแก้ก่อนเดโม (เฮียสั่งตรง ๆ ว่า "ผิด ต้องแก้")

### P0-1 · Companies: ต้องโชว์ "ทุกบริษัท" แม้ 0 โครงการ 🐛 (bug ยืนยันในโค้ด)
- **เฮียสั่ง (คลิป4 บรรทัด 65-96):** บริษัทที่ยังไม่มีโครงการ ตอนนี้ **ไม่โชว์** → เฮียบอก **"ผิดแล้ว... ต้องการให้มันโชว์ทั้งหมด"**. หลักการ: ทุกบริษัทต้องโผล่ในรายการ ส่วนจะมี 0 / 1 / หลายโครงการเป็นอีกเรื่อง
- **บั๊กจริงในโค้ด:** `src/pages/OwnerProjects.tsx:222` → `.filter((row) => row.projectCount > 0)` กรองบริษัท 0 โครงการทิ้ง
- **แก้:** เอา `.filter(projectCount > 0)` ออก (หรือเปลี่ยนเป็นโชว์ทั้งหมด เรียงตาม projectCount). แถวที่ 0 โครงการให้โชว์ "0/50" อย่างซื่อสัตย์ (ตรงกับกฎ KK #8 ในแผน: ไม่ซ่อนแถวที่ data ว่าง)
- **acceptance:** บริษัทใน DB ที่ยังไม่มี property โผล่ในตาราง Companies พร้อมเลข `0/<limit>` · ไม่มีบริษัทหายไปจากรายการ

### P0-2 · "Market Overview" คือชื่อผิด → เปลี่ยนเป็น "Sell Overview"
- **เฮียสั่ง (คลิป3 บรรทัด 7-10; คลิป4 บรรทัด 110-159):** หน้านี้โชว์แค่ "ยอดขาย" = **Sell/Selling ไม่ใช่ Marketing**. เฮียอธิบายว่า Marketing = "กระบวนการส่งมอบคุณค่าของสินค้า/บริการให้ลูกค้า" (โฆษณา/แคมเปญ) — ไม่ใช่ยอดขาย
- **แก้ที่:** `src/pages/OwnerMarket.tsx:214` หัวข้อ `Market Overview` → **`Sell Overview`** (เนื้อห้าในกราฟ "ยอดขายตามช่วงราคา/ประเภท/แนวโน้ม" ถูกแล้ว คงไว้)
- **หมายเหตุ:** เฮีย "ไม่ได้บอกให้ทำ Market จริง" ตอนนี้ — แค่เปลี่ยนคำให้ถูก. (ของจริง "สภาวะตลาดอสังหา" + "Marketing Campaign Overview" = งานทีหลัง ดู P2-2)
- **acceptance:** หัวหน้า + เมนูใช้คำ "Sell Overview" (ไทย: ภาพรวมยอดขาย) · ไม่มีคำว่า Market บนหน้าที่โชว์แค่ยอดขาย

### P0-3 · Company Performance + Sales Performance: การ์ดภาพรวมต้องเป็น "โดนัท/วงกลม" ไม่ใช่กราฟ/ตารางเดิม
- **เฮียสั่ง (คลิป3 บรรทัด 27-43):** หน้า "ภาพรวมบริษัท" และ "ภาพรวมเซลล์" — ตัวภาพรวมต้องเป็น **โดนัทชาร์ต (pie/donut)** เพื่อเห็นสัดส่วน: ก้อนใหญ่สุดคือใคร, เอาเมาส์ชี้เห็นชื่อ+มูลค่า (สมมุติมี 20-30 บริษัท)
- **สถานะปัจจุบัน:** `OwnerCompanies.tsx` + `OwnerAgents.tsx` ใช้ **ตารางอันดับ (ranking table)** เป็นหลัก — ยังไม่มี donut ภาพรวม

- **acceptance:** ทั้ง 2 หน้ามี donut ด้านบน · hover เห็น ชื่อ+มูลค่า · ตารางอันดับยังอยู่ใต้กราฟ

### P0-4 · Audit Log: ต้องจัด "ใหญ่→เล็ก" + filter เดือน (ไม่ใช่ flat list 200 แถว)
- **เฮียสั่ง (คลิป3 บรรทัด 114-125; คลิป4 บรรทัด 1-13):** audit log ปัจจุบัน "ดูไม่รู้เรื่อง ยาวเป็นพืด". ต้อง:
  1. **จัดกลุ่มจากใหญ่→เล็ก** — ระบุให้เห็นว่าเป็น **บริษัทไหน / โครงการไหน** ก่อน (group/breadcrumb) แล้วค่อย feed รายการลงไป
  2. มี **filter เดือน** (เฮีย: "ดูเป็นเดือนมั้ย... ยาว 100 กว่า ทำไง" คลิป4 บรรทัด 9-10)
- **สถานะปัจจุบัน:** `OwnerAudit.tsx:110` → `.limit(200)` flat list, มี filter หมวด(cat)+search แต่ **ไม่มี filter เดือน** และ **ไม่ group ตามบริษัท/โครงการ**
- **แก้:**
  - เพิ่ม **month filter** (dropdown เดือน) — มี `created_at` อยู่แล้ว
  - จัดกลุ่มตาม **บริษัท (tenant)** เป็นชั้นบน (มี `tenant_id` + `tenantName` map อยู่แล้ว) — แสดงหัวกลุ่มบริษัท แล้ว list ใต้กลุ่ม (โครงการถ้ามี project context ใน log)
- **acceptance:** เลือกเดือนแล้ว list กรองตามเดือน · log จัดกลุ่ม/ติดป้ายบริษัท ชัดเจน อ่านรู้เรื่อง

## 2. P1 — สำคัญแต่ทำต่อได้ (เฮียชี้ทิศ ยังไม่บล็อกเดโม)

### P1-1 · Sell Overview ต้อง filter รายเดือนได้
- **เฮียสั่ง (คลิป4 บรรทัด 159-164):** "sell ไม่พอนะ เดือนไหน — ต้องดูแต่ละเดือนได้ด้วย". เวลาวิเคราะห์ปัญหา ต้องดูได้ว่าเดือนนี้เทียบเดือนก่อนเป็นไง
- **แก้:** เพิ่ม month selector ใน `OwnerMarket.tsx` (Sell Overview) ให้กรองยอดขายตามเดือน
- **acceptance:** เลือกเดือน → กราฟ 3 ตัว (ช่วงราคา/ประเภท/แนวโน้ม) อัปเดตตามเดือน

### P1-2 · Geography: ต้องเจาะลึกถึง "อำเภอ/เขต" ไม่ใช่แค่จังหวัด
- **เฮียสั่ง (คลิป4 บรรทัด 165-174):** ทำเลตอนนี้มีแค่ภาพรวม "จังหวัด" — เฮียอยากเห็นระดับ **เขต(กทม.) / อำเภอ** (เชียงใหม่ = อ.เมือง หรือ อมก๋อย?). นี่คือ "Advance" ที่ทำให้แนะนำลูกค้าได้ ("โซนนี้ขายดี")
- **ข้อมูล:** `properties.address` เป็น JSON — เช็คว่ามี `district`/`amphoe`/`subdistrict` ไหม (Phase 0 เดิมยืนยันแค่ `province`). ถ้าไม่มี = ทำ note ไว้ ไม่ใส่กราฟลวง
- **acceptance:** drill จังหวัด → เห็น breakdown ระดับอำเภอ/เขต (ถ้า data พอ) · ถ้าไม่พอ = note ชัดเจน

### P1-3 · PDPA Consent capture (เซลล์เก็บข้อมูลลูกค้าผ่าน device แพลตฟอร์ม)
- **เฮียสั่ง (คลิป3 บรรทัด 92-108):** PDPA. 2 ช่องทาง:
  1. **เซลล์ถือ tablet ที่โครงการ** เก็บข้อมูลลูกค้า → ต้องมี **หน้า consent ลายเซ็น** (Touch bar / เซ็นนิ้ว / กดยินยอม) ก่อนเก็บ. ป๊อปอัปสไตล์ "เปิดแอปธนาคาร"
  2. **ลูกค้าแอด LINE / สแกน QR (LINE bot integration)** → ขอ consent ตรง QR/LINE ตอนนั้นเลย
- **เหตุผลเฮีย:** "ไม่งั้นโดนฟ้อง 5 ล้าน/เคส" (คลิป3 บรรทัด 103)
- **สถานะ:** ยังไม่ทำ (ดู memory `project_support_ticket_plan` แยกเรื่อง). ตอนนี้ silent attribution ผ่าน `?ref=` ทำแค่ agent
- **acceptance:** มี consent gate (ลายเซ็น/กดยินยอม) ก่อนบันทึก lead จาก device เซลล์ · เก็บ timestamp+หลักฐาน consent
- **อัปเดต 2026-06-12 (เช็คโค้ดแล้ว):** ฝั่ง tenant **มีอยู่แล้ว** — `AddLeadModal`/`EditLeadModal` มี signature pad เต็ม (เลือก "ยินยอม" → ป๊อปอัปนโยบาย → กด "ยอมรับนโยบาย" → ลายเซ็นโผล่ → เก็บลง `customers.preferences.signature`+`consent_given`). ที่ยังขาด = consent ผ่าน LINE bot (อีก path)
- **platform_leads (Owner B2B) ไม่ต้องมีลายเซ็น** — เป็น CRM ภายในที่ทีมเรากรอกเอง, B2B legitimate-interest; signature ไม่เหมาะ (ลูกค้าไม่ได้อยู่ให้เซ็น)

### P1-3b · 🔴 GAP สำคัญ — DPA / การส่งมอบแพลตฟอร์มให้ tenant (โซ่ PDPA ผู้ควบคุม↔ผู้ประมวลผล)
- **ที่มา:** เฮียถามตอนพรีเซนต์ "เราจะส่งมอบยังไง" → ตีความ = ตอนส่งมอบแพลตฟอร์มให้บริษัท tenant ต้องมีข้อตกลงอะไร
- **โซ่ PDPA:** ลูกค้าซื้อบ้าน →[เซ็นยินยอม ✅]→ tenant (ผู้ควบคุมข้อมูล) →[**DPA ❌ ขาด**]→ เรา (ผู้ประมวลผล). PDPA ม.40 บังคับมี DPA ระหว่าง controller↔processor — DPA นี่แหละที่ทำให้ Owner ถือ+เห็นข้อมูลข้ามทุก tenant ได้ถูกกฎหมาย
- **สถานะโค้ด:** `RegisterForm` มีติ๊ก agreeTerms+agreePrivacy แต่ลิงก์เอกสารเป็น `href="#"` (ยังไม่มีเอกสารจริง) · **ไม่มี DPA เลย**
- **ต้องทำ 2 ส่วน:** (1) เอกสารจริง ToS/Privacy/**DPA** — ต้องมาจากฝ่ายธุรกิจ/ทนาย (โค้ดแทนไม่ได้); (2) หน้ายอมรับ + ตารางเก็บหลักฐาน (ใครยอมรับ DPA version ไหน เมื่อไหร่) ตอน onboard tenant — โค้ดทำได้ (อาจต้อง table ใหม่ = ขออนุมัติ migration)
- **ความเห็น:** สำคัญสำหรับ production · ยกให้เฮียตัดสิน + รอเอกสารกฎหมาย ก่อนลงมือโค้ด

## 3. P2 — ทำทีหลัง / ของจริงเฟสถัดไป (เฮียพูดถึงเป็นวิสัยทัศน์)

### P2-1 · Sales Performance — เหตุผลเชิงธุรกิจ (ทำไม Owner ต้องดู perf เซลล์)
- **บริบท (คลิป3 บรรทัด 44-76):** เฮียอธิบาย use case — Owner ดู perf เซลล์เพื่อ:
  - เซลล์เก่ง → "จีบมาขายให้ลูกค้าเราบางคน"
  - เซลล์เปิดยูนิตให้ลูกค้าดูบ่อย **แต่ขายไม่ได้** → สัญญาณว่า "มีอะไรประหลาด" (ราคาแพงไป / ทำเลมีปัญหา เช่น กำแพง/หม้อแปลงไฟ/เมรุเผาศพ)
  - **insight ที่ควรมี:** ยูนิตที่ "เปิดดูบ่อย แต่ปิดไม่ได้" = flag ให้วิเคราะห์สาเหตุ
- **ทำได้จาก data:** `property_views` (เปิดดูบ่อย) + `units.status` (ขาย/ไม่ขาย) → metric "ดูเยอะ-ปิดต่ำ"
- **ขอบเขต PDPA:** หยุดที่ระดับ performance/aggregate — ห้ามเจาะ PII ลูกค้ารายคนของบริษัทอื่น (ตามแผน §8)

### P2-2 · Marketing Campaign Overview (ของจริง "Marketing" ที่เฮียอยากได้)
- **เฮียสั่ง (คลิป4 บรรทัด 144-148):** หลังแก้ Sell Overview แล้ว → ทำหน้า **Marketing Campaign Overview** จริง: แต่ละบริษัทยิงแคมเปญอะไร, แคมเปญไหน broadcast ไปเยอะสุด, **segment ไหนตอบสนองเยอะสุด** — "อันนี้ดิมีประโยชน์"
- **ของมีอยู่:** ระบบแคมเปญ + segment (11 segment) มีแล้ว → ทำ analytics overlay
- **acceptance:** หน้าใหม่แยกจาก Sell Overview · โชว์ผลแคมเปญ + segment performance

### P2-3 · Audit/Company drill-down ครบชั้น (โครงการ → ยูนิต/หลัง)
- **บริบท (คลิป4 บรรทัด 98-107):** Company → คลิกดูโครงการ → คลิกโครงการดูเป็น "หลัง/ยูนิต". เฮีย: "จากใหญ่เป็นเล็ก ถูกแล้ว" แต่ตอนนี้ **กดจากโครงการลงยูนิตยังไม่ได้** (คลิป4 บรรทัด 104 "ทำไม่ได้ กดมาไม่ได้")
- **แก้:** wire drill-down โครงการ → ยูนิต ให้คลิกได้ครบ chain

### P2-4 · กรณีบริษัท "7 หลังในโครงการเดียว" — นิยาม project vs unit ให้ชัด
- **บริบท (คลิป4 บรรทัด 26-42):** เฮียอธิบายเคส B (เช่น 7 หลัง) = **1 โครงการ ที่มี 7 ยูนิต/หลัง** ไม่ใช่ 7 โครงการ. ทุกบริษัทมี ≥1 โครงการ; ความต่างคือมี 1 หรือ ≥2 โครงการ. การนับ "X/50" = นับ "โครงการ" ไม่ใช่หลัง
- **acceptance:** การนับ projectCount ตรงนิยามนี้ (7 หลัง = 1 โครงการ) · "X/50" = จำนวนโครงการเทียบ plan limit

## 7. ภาคผนวก — ที่มา CHATEAU (จากคลิปสหกิจ · ใช้ตอน pitch/present ไม่ใช่ requirement งาน)

**Pain point ที่ CHATEAU แก้ (คลิปสหกิจ บรรทัด 48-59):**
- เครื่องมือการตลาดอสังหาทั้งหมด = สร้าง lead + ทำให้คนมาดูโครงการ → "จบแค่หน้าบ้าน". **พอลูกค้าก้าวพ้นประตูโครงการ ไม่มีเครื่องมืออะไรช่วยเซลล์ขายเลย** — มีแค่กระดาษลงทะเบียน + ทักษะเซลล์แยก quality (A/B/C). ปัญหา: เอกสารหาย / เซลล์ย้าย / เซลล์ใหม่ห่วย

**3 คุณค่าหลักของ CHATEAU (บรรทัด 64-67):**
1. **เก็บ data ลูกค้าบนระบบออนไลน์** → เจ้าของเห็นทันที (ไม่พึ่งกระดาษ/เซลล์)
2. **ไม่ต้องพึ่งเซลล์เก่ง/ไม่เก่ง** → ใช้ Algorithm / Random Forest Data Model แยก Quality ลูกค้า
3. **Financial Score** → ตลาดอสังหาจริงคือ "ตลาดของธนาคาร" (ธนาคารไม่ปล่อยกู้ = ขายไม่ได้). คำนวณ pre-approve เบื้องต้น (รายได้/หนี้รถ) → เซลล์รู้ว่าควรตามใครก่อน

**2 score ที่เซลล์ได้:** Quality Score + Financial Score → จัดลำดับการตาม lead

**Lead involvement model (บรรทัด 8-46):** สินค้าแบ่งตามการตัดสินใจ — Low (e-commerce กดซื้อเลย) / Medium (โรงแรม) / **High Involvement (อสังหา/รถ/ประกัน)** ต้องมาดูจริงก่อนซื้อ. lead อสังหา = lead quality สูง. แยก hot/warm/cold → ตาม hot ก่อน. **นิยาม hot = "ลูกค้ามาดูบ้าน/โครงการแล้ว"** (ทักมาถามแต่ไม่มาดู = ไม่มีทางซื้อ)

**ที่มาชื่อ + concept (บรรทัด 79-102):** มาจากการแยก "คาแรคเตอร์ผู้บริโภค" (ซีรีส์/โค้ก-เปปซี่) → คนซื้ออสังหามีคาแรคเตอร์ → ใช้ data model แยก. **ชื่อ "Chateau"** = มาจากชื่อไวน์ฝรั่งเศส (Château) แปลว่า "ปราสาท" = อสังหา

**จุดขาย (บรรทัด 107):** ในตลาดมี CDP (Customer Data Platform) สำหรับ CRM ทั่วไป **แต่ไม่มี CDP สำหรับธุรกิจอสังหาโดยตรง** = ช่องว่างที่ CHATEAU จับ
